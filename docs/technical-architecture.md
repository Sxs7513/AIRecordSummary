# AI 录音检索产品技术架构设计文档

> 架构演进说明：任务调度、实时状态和流式生成的最新目标架构参见 [`redis-kafka-architecture-refactor.md`](./redis-kafka-architecture-refactor.md)。该方案采用 Kafka-first：Kafka 保存任务与过程事实，Redis 保存活跃状态与实时流，PostgreSQL 保存最终业务结果与查询投影；相关结论优先于本文早期 MVP 队列描述。

## 1. 文档目标

本文档用于定义产品第一阶段的技术架构、核心模块、关键数据流、主要技术选型方向和后续扩展预留点。

当前设计面向 MVP，目标是优先保证以下三件事：

- 录音可稳定转写并沉淀为结构化数据
- 用户问题可通过检索拿到高相关证据
- 模型输出可基于证据生成可信回答
- 系统可区分录音中的不同说话人，并识别重点目标人物

## 2. 架构设计原则

### 2.1 以可控 RAG 工作流为核心

产品核心竞争力是“找得到、答得可信、证据可回放”。在线问答链路采用 RAG 为主，并使用 LangGraph 编排 LLM router、检索执行、证据评估、二次检索、回答生成和引用校验。LangGraph 是 Phase 2 RAG 工作流的一部分，不是后续预留项。

### 2.2 在线链路与离线处理分离

音频转写、切分、向量化属于重处理任务，应走异步离线链路；搜索和回答属于交互链路，应尽量轻量、稳定、低延迟。

### 2.3 回答必须可追溯

任何模型回答都必须能回链到原始 chunk、录音和时间点。系统设计上要优先保证“证据可见”。

### 2.4 选型要利于迭代

MVP 阶段避免过早引入过重基础设施，但要保持模型、检索策略和 LangGraph node 的接口边界清晰，便于后续替换模型、扩展检索和增加更多工作流分支。

### 2.5 说话人能力分层设计

说话人相关能力应拆为两层：

- 说话人分离：区分同一条录音中的不同说话人，并赋予稳定匿名标签，如 `Speaker A`
- 目标人物识别：基于已知参考样本，判断某些片段是否属于指定人物

这样可以避免把“区分不同人”和“识别具体是谁”混为一谈。

## 3. 总体模块划分

系统可以拆成以下几个核心层：

### 3.1 前端应用层

使用 `Next.js` 提供统一 Web 应用，负责：

- 录音上传
- 列表浏览
- 搜索输入
- AI 回答展示
- 引用片段展示
- 音频播放和时间点跳转

### 3.2 应用服务层

负责处理业务请求和 API 编排，包括：

- 文件上传管理
- 录音元数据管理
- 搜索请求处理
- 检索结果聚合
- 调用大模型生成回答
- 任务状态查询

### 3.3 异步处理层

负责重任务处理，包括：

- 音频预处理
- Whisper 转写
- 说话人分离
- 目标人物识别
- 文本清洗
- chunk 切分
- embedding 生成
- 索引构建

### 3.4 数据与索引层

负责持久化和检索能力，包括：

- 关系型数据库
- 对象存储
- 全文检索能力
- 向量检索能力

### 3.5 模型能力层

负责接入外部或自托管模型，包括：

- 语音转写模型
- 说话人分离模型
- 声纹比对模型
- 文本向量模型
- 问答生成模型

## 4. 核心数据流设计

### 4.1 录音入库链路

1. 用户上传音频文件
2. 文件保存到对象存储或本地文件存储
3. 应用服务创建 `recording` 与 `processing_job`
4. 异步任务消费队列，拉起转写和说话人处理流程
5. Whisper 输出带时间戳的转写结果
6. 说话人分离模型输出说话片段及匿名身份，如 `Speaker A`
7. 目标人物识别模块将说话片段与参考样本做比对
8. 系统对文本做清洗、切分，并继承说话人标签
9. 为每个 chunk 生成 embedding
10. chunk、说话人标签和识别结果写入数据库与检索索引
11. 任务状态更新为完成

### 4.2 搜索问答链路

1. 用户输入自然语言问题
2. LangGraph router 将 query 转为结构化 retrieval plan
3. 如 query 包含人物名，后续通过独立 `resolvePeople` 节点把 `personNames` 映射为 `speakerProfileIds`
4. 检索执行器按 strategy 选择向量检索、日期范围总结、最近录音总结或范围内主题检索
5. 对召回结果进行证据充分性判断，必要时重写 query 并二次检索
6. 选出若干高相关 chunk 或录音上下文作为证据
7. 调用大模型生成回答，并校验引用和证据一致性
8. 返回回答、引用片段、录音信息、时间点、说话人标签和目标人物标记

## 5. 技术选型建议

### 5.1 前端与服务层

- 框架：`Next.js`
- 原因：
  - 前后端一体化，适合快速启动
  - 页面、接口、服务端逻辑可以统一管理
  - 适合后续扩展鉴权、后台任务页面、管理页面

建议做法：

- 前端页面和 API 统一放在 Next.js 项目中
- 重处理任务不要放在请求链路中同步执行

### 5.2 数据库

- 首选：`PostgreSQL`
- 原因：
  - 适合保存业务实体和关系数据
  - 可扩展性强
  - 后续可结合 `pgvector` 进行一体化存储

MVP 阶段建议优先保存：

- 录音元数据
- 转写文本
- chunk 数据
- 任务状态
- 查询日志

### 5.3 向量检索

可选方案：

- `PostgreSQL + pgvector`
- 独立向量数据库

MVP 建议：

- 优先使用 `PostgreSQL + pgvector`

原因：

- 基础设施更轻
- 便于快速开发
- 数据一致性更容易管理

### 5.4 全文检索

MVP 建议优先使用数据库自带全文检索能力，后续若数据量显著增长，再考虑引入独立搜索引擎。

### 5.5 转写模型

- 首选方向：`Whisper` 体系
- 部署建议：优先后端异步处理，而不是依赖用户本机设备

原因：

- 更稳定
- 易于统一质量
- 易于控制模型版本和资源消耗

### 5.6 说话人分离与目标人物识别

说话人能力建议拆成两套处理：

- 说话人分离：负责把单条录音内的多人发言区分开，并输出稳定匿名标签
- 目标人物识别：负责将某个说话片段与已知重要人物的参考样本比对

MVP 的推荐输出：

- 单条录音内，每个发言片段带 `speaker_label`
- 对重点目标人物，增加 `is_target_person` 与 `confidence`

设计建议：

- 不把识别结果当作绝对真值
- UI 上要明确展示低置信度待确认状态
- 先支持少量重点人物，不急于做完整人物库

推荐工具组合：

- 转写：`Whisper`
- 说话人分离：`pyannote.audio`
- 目标人物识别：`SpeechBrain` 的 speaker recognition / verification 能力

推荐原因：

- `Whisper` 适合负责中文语音转文字和时间戳输出
- `pyannote.audio` 适合把单条录音中的不同人区分为匿名说话人，如 `Speaker A/B/C`
- `SpeechBrain` 更适合把录音片段与已知人物参考样本做相似度比对

对应职责边界：

- `Whisper` 负责“说了什么”
- `pyannote.audio` 负责“这段话属于哪个匿名说话人”
- `SpeechBrain` 负责“这个匿名说话人是不是重点目标人物”

MVP 推荐实现链路：

1. 使用 `Whisper` 完成整条录音转写，输出文本和时间戳
2. 使用 `pyannote.audio` 对录音做说话人分离，得到说话片段及 `Speaker A/B/C`
3. 将说话片段与转写结果对齐
4. 使用 `SpeechBrain` 对每个说话片段和目标人物参考样本做比对
5. 将识别结果写回 `transcription_segment` 或独立的说话人结果表

替代方案与演进建议：

- 如果后期需要更强的 GPU 友好能力和更完整的语音流水线，可评估 `NVIDIA NeMo`
- 如果后期希望接入更成熟的商业化说话人能力，可评估 `pyannoteAI` 或其他商业服务
- MVP 阶段不建议一开始就依赖重型商业服务，优先采用开源组合验证产品价值

### 5.7 问答模型

要求：

- 支持中文理解与总结
- 支持较好的指令遵循
- 能基于给定上下文输出结构化结果

MVP 阶段建议：

- 将问答模型作为可替换适配层接入
- 不把模型能力直接耦合到业务逻辑中

用于保存录音基础信息：

- `id`

- `file_name`
- `file_path` 或对象存储 key
- `duration_seconds`
- `status`
- `created_at`
- `updated_at`

### 6.2 transcription

- `id`
- `recording_id`
- `full_text`
- `language`
- `model_name`
- `created_at`

### 6.3 transcription_segment

用于保存转写原始片段或 chunk，以及对应的说话人信息：

- `id`
- `recording_id`
- `transcription_id`
- `content`
- `start_ms`
- `end_ms`
- `chunk_index`
- `speaker_label`
- `speaker_cluster_id`
- `speaker_confidence`
- `is_target_person`
- `target_person_confidence`
- `embedding`
- `metadata`

说明：

- 如果需要区分“原始转写 segment”和“检索 chunk”，可拆成两张表
- MVP 也可以先合并为一张表，降低复杂度

### 6.4 speaker_profile

用于保存已知人物的声纹参考信息：

- `id`
- `display_name`
- `status`
- `notes`
- `created_at`
- `updated_at`

### 6.5 speaker_profile_sample

用于保存某个人物的参考音频样本：

- `id`
- `speaker_profile_id`
- `file_path` 或对象存储 key
- `duration_seconds`
- `embedding` 或声纹特征引用
- `created_at`

### 6.6 processing_job

用于保存异步处理任务：

- `id`
- `recording_id`
- `job_type`
- `status`
- `error_message`
- `started_at`
- `finished_at`

说明：

- `job_type` 需要覆盖 `transcription`、`speaker_diarization`、`speaker_identification`、`indexing`

### 6.7 search_log

用于记录搜索行为，便于后续优化：

- `id`
- `query`
- `top_results`
- `response_time_ms`
- `created_at`

## 7. 说话人能力设计

### 7.1 说话人分离

目标：

- 在单条录音内部区分不同说话人
- 生成稳定匿名标签，如 `Speaker A`、`Speaker B`
- 将标签贯穿到转写、检索和播放链路

设计原则：

- 匿名标签只保证单条录音内稳定，不默认跨录音复用
- 重叠说话、噪音和极短发言会降低效果
- UI 上应允许展示“未知说话人”或低置信度标记

### 7.2 目标人物识别

目标：

- 对某个已知重要人物进行专门识别
- 判断其是否出现在录音中，以及出现在哪些时间段

输入前提：

- 需要至少一段已确认身份的参考音频
- 参考样本应尽量清晰、干净、时长足够

输出建议：

- `is_target_person`
- `target_person_confidence`
- `matched_profile_id`

### 7.3 为什么两者都要做

如果只做目标人物识别，你可以知道“这个人是否出现过”，但无法很好地组织整条录音中的多人结构。

如果只做说话人分离，你可以得到 `Speaker A/B/C`，但无法知道其中谁是重点人物。

因此对当前产品，最佳做法是：

- 先做录音内的说话人区分
- 再在分离后的片段上做目标人物识别

## 8. 检索策略设计

### 7.1 为什么不能只做向量检索

录音查询中有很多明确实体，如人名、日期、预算、产品名、专有名词。单纯向量检索在这类精确命中上不一定稳定，因此建议采用混合检索。

### 7.2 混合检索建议

第一阶段建议组合以下能力：

- 全文检索：负责精确关键词召回
- 向量检索：负责语义相似召回
- 说话人过滤：支持按 `speaker_label` 或目标人物命中过滤
- 人物解析预留：router 输出 `personNames`，后续 resolver 再映射到 `speaker_profiles.id`
- 简单重排：根据得分、时间邻近性、字段权重进行合并排序

### 7.3 chunk 设计原则

chunk 切分直接决定检索质量。建议：

- 不要只按固定字数切
- 尽量结合时间戳和语义边界
- chunk 不宜过长，否则噪音过大
- chunk 之间可以保留少量重叠

MVP 可采用务实策略：

- 优先基于时间片或句段切分
- 每个 chunk 保留前后少量上下文
- 尽量避免把两个不同说话人的连续发言切进同一个 chunk
- 后续再根据实际效果迭代

## 9. AI 回答层设计

### 8.1 回答模式

回答服务应遵循“先检索，后生成”的模式：

- 不允许模型直接基于参数记忆回答
- 必须只基于检索出的上下文回答
- 输出中要包含来源引用

### 8.2 输出结构建议

MVP 阶段建议返回结构化结果：

- `answer`
- `citations`
- `matched_segments`
- `confidence` 或内部评分

### 8.3 Prompt 约束建议

模型提示词应强调：

- 仅根据提供的上下文作答
- 找不到时明确说明证据不足
- 优先引用原始说法
- 避免编造未出现的信息

## 10. 异步任务设计

MVP 阶段建议将以下任务异步化：

- 音频转写
- 说话人分离
- 目标人物识别
- embedding 生成
- 索引更新

任务队列可根据实际技术栈选择轻量方案，关键要求是：

- 可重试
- 可观测
- 状态可回查
- 不阻塞用户请求链路

## 11. 安全与隐私考虑

录音通常包含敏感信息，MVP 即使不做完整企业安全体系，也建议至少考虑：

- 文件访问控制
- 模型调用过程中的敏感数据边界
- 日志中避免泄露完整敏感文本
- 删除录音时的数据清理策略

如果后续面向企业客户，需进一步考虑：

- 私有化部署
- 数据隔离
- 审计日志
- 存储加密

## 12. 可观测性建议

建议记录以下监控与日志：

- 上传成功率
- 转写成功率
- 说话人分离成功率
- 目标人物识别后的人工确认准确率
- 转写耗时
- 说话人处理耗时
- embedding 生成耗时
- 搜索响应时间
- 问答响应时间
- 搜索结果点击率
- 任务失败原因统计

## 13. MVP 阶段不建议过早引入的复杂度

- 多 Agent 协作流程
- 独立微服务拆分
- 多种向量数据库并存
- 复杂权限体系
- 过度优化的实时处理链路
- 跨录音全局统一的说话人画像系统

## 14. 后续演进路线

### 13.1 近一步演进

- 增加 query rewrite
- 增加多路召回
- 增加 rerank
- 增加录音级摘要和标签提取
- 增加目标人物维度的筛选与统计视图

### 13.2 LangGraph 工作流增强

Phase 2 已使用 LangGraph 编排在线 RAG。后续演进重点不是“是否引入 LangGraph”，而是扩展 graph 能力：

- 为多轮追问增加 checkpoint 和会话状态恢复
- 为多次检索和多步判断增加更细的条件边
- 为跨多条录音聚合分析增加专门 retrieval node
- 增加 `resolvePeople` node，将人名、别名或前端选择结果解析为目标人物过滤条件
- 接入外部工具时增加受控 tool node
- 持久化 graph execution trace，便于审计和调试

### 13.3 企业化演进

- 多用户与多工作空间
- 权限与分享
- 更高性能检索架构
- 私有部署与合规支持
- 跨录音统一人物身份管理

## 15. 当前推荐结论

对于第一阶段，推荐采用以下务实架构：

- `Next.js` 作为统一 Web 应用与 API 层
- `PostgreSQL` 作为主数据库
- `pgvector` 承载 MVP 向量检索
- `Whisper` 作为后端异步转写能力
- 说话人分离 + 目标人物识别作为独立异步处理链路
- 混合检索作为核心能力
- 大模型只负责基于证据总结回答

这个组合的优点是：

- 架构简单
- 便于快速验证
- 足够支撑第一版产品闭环
- 后续可以平滑演进到更复杂的 Agent 架构
